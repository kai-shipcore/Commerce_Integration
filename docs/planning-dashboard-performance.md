# Planning AG Grid 로딩 최적화 검증

검증일: 2026-09-11. 대상: `/forecast/planning/dashboard-ag-grid`.

## 변경 범위

- 상세 전용 `/api/planning/dashboard/container-details` 추가. 컨테이너 헤더·카테고리·SKU 상세만 조회하며 기본 통계, 판매량, 재고 집계, 과거 판매량 snapshot, last-sync를 재조회하지 않는다.
- 기존 전체 API와 신규 API가 동일한 상세 매핑 함수를 사용한다. 헤더 정렬, 수량 0, null, 할당량 기본값, 중복 항목의 마지막 값 우선 처리, `rawContainers=1`의 `status != 'complete'` 범위를 유지한다. 특히 raw 조회는 기존처럼 includeDrafts=false여도 draft 상세를 포함할 수 있다.
- 신규 응답은 별도 타입과 `containers-only-v1:` 캐시 variant로 분리한다. 기존 `planning:dashboard:*` 무효화 범위와 5분 TTL을 유지한다.
- 훅은 기본 행 집합을 유지하고 SKU별 상세만 병합한다. 동일 설정의 객체 재생성에 따른 중복 요청을 제거하고, 조건 변경/언마운트 때 이전 요청을 취소하며 요청 소유권으로 늦은 응답과 finally 처리를 차단한다.
- 고정 600ms 대기를 제거한다. 기본 조회가 현재 조건으로 완료되고 컨테이너 그룹이 표시되면 상세를 요청한다. 컨테이너 표시 시 상세 도착 전 전체 SKU 체인 계산을 한 번 생략한다. 계산식 자체는 변경하지 않는다.
- 앞서 수정된 탭 코드와 + 버튼 제거를 보존한다. 스크롤 단위 조회, Worker, 조회 범위 축소는 적용하지 않는다.

## 성능 측정

실제 로그인 계정의 SC 4,700행, custom 모드, 동일 사용자 설정으로 변경 전후 각각 최초 방문 5회/재방문 5회. Chromium headless, 1440×1000, 이미 실행 중인 로컬 Next 개발 서버. 최초 방문은 새 브라우저 context, 재방문은 같은 context에서 전체 문서 재탐색이며 SPA 메모리 캐시 재방문과는 다르다. 설정 저장 등 로그인 외 API 쓰기는 차단했다.

첫 행 시간은 AG Grid 행 DOM 표시 시점, 컨테이너 완료 시간은 상세 응답 수신 후 React 반영 대기(250ms), 컨테이너 수량 열 존재와 계산/로딩 표시 종료를 모두 확인한 시점이다. 두 버전에 같은 측정 코드를 사용했다.

| 지표 (5회 중앙값) | 변경 전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 최초 방문 첫 행 | 3,372ms | 1,990ms | 41.0% |
| 최초 방문 컨테이너 완료 | 7,648ms | 5,465ms | 28.5% |
| 재방문 첫 행 | 3,103ms | 2,037ms | 34.4% |
| 재방문 컨테이너 완료 | 7,579ms | 5,412ms | 28.6% |
| 대시보드 API 요청/방문 | 6회 | 2회 | 66.7% |
| 대시보드 JSON 본문 합계/방문 | 40,644,551 bytes | 7,692,855 bytes | 81.1% |
| 상세 JSON 본문 | 7,596,041 bytes | 1,083,153 bytes | 85.7% |

기존 요청은 기본 5회+전체 상세 1회, 변경 후는 기본 1회+전용 상세 1회였다. 위 크기는 압축 해제된 응답 본문 크기이며 HTTP 압축/헤더를 포함하는 실제 네트워크 전송 바이트는 아니다. 나머지 사용자 설정·SKU 메모 API는 요청 수에서 제외했다.

| 회차 | 최초 전: 첫 행/완료 ms | 최초 후: 첫 행/완료 ms | 재방문 전: 첫 행/완료 ms | 재방문 후: 첫 행/완료 ms |
| --- | --- | --- | --- | --- |
| 1 | 3980 / 8658 | 2631 / 7010 | 2942 / 7495 | 2101 / 6058 |
| 2 | 3419 / 8018 | 2097 / 5791 | 3119 / 7665 | 1945 / 5263 |
| 3 | 3235 / 7591 | 1912 / 5398 | 3399 / 7755 | 2066 / 5412 |
| 4 | 3372 / 7582 | 1921 / 5465 | 3103 / 7490 | 1580 / 5086 |
| 5 | 3236 / 7648 | 1990 / 5413 | 2999 / 7579 | 2037 / 5848 |

기본 응답은 변경 전 전부 cache HIT, 변경 후 3회차 재방문만 MISS였다. 상세 응답은 양쪽 첫 회만 MISS이고 나머지는 HIT였다. TTL과 캐시를 인위적으로 변경하지 않았다. 최초 서버 시작/콜드 컴파일 시간은 별도 측정하지 못했으므로 위 수치를 콜드 스타트나 운영 배포 성능으로 해석하면 안 된다. DB 전체 snapshot을 고정하지는 않았으나 모든 측정에서 행 수와 본문 크기가 같았다.

원시 기록(로컬 gitignored): `tmp/planning-performance/planning-load-before-verified.json`, `tmp/planning-performance/planning-load-after-verified.json`. 재측정: `node scripts/benchmark-planning-load.mjs <label>` (`.env.e2e.local`의 테스트 계정 필요).

## 데이터 동등성과 기능 검사

고정 입력 단위 테스트: 헤더 ETA/이름 정렬, 카테고리/복수 카테고리, 모드/날짜/draft 옵션, 상세 없는 SKU, 0/null, 중복 항목, 할당량, 기존 상세와 병합 결과 동등성. 전용 상세에서 기본 통계·재고·판매량·last-sync 조회가 호출되지 않는 것도 검사했다.

실제 인증된 API를 읽기 전용으로 비교했으며 각 기본 행의 컨테이너 맵과 전체 컨테이너 헤더가 일치했다.

| 조회 조건 | 비교 행 수 | 기존 본문 bytes | 신규 본문 bytes |
| --- | ---: | ---: | ---: |
| SC / custom | 4,700 | 7,596,041 | 1,083,153 |
| CC+SWC+AC / link | 1,372 | 2,498,445 | 583,868 |
| FM / custom / includeDrafts | 5,504 | 7,580,191 | 59,943 |
| SC / link / 2026-08-01 | 4,684 | 7,574,149 | 1,083,153 |

브라우저 편집 검사는 실제 UI와 메모리 모의 API를 사용했다. 정렬, 검색 필터, 필터된 Excel의 실제 파일 내용, Copy Live, 수량 10→17 저장, Live/시나리오 전환, Duplicate, Apply to Live 확인, ETA 편집, 자동 발주 계산 및 별도 저장, 새로고침 후 시나리오 복원까지 검사한다. 서버 저장/Apply의 실제 DB 트랜잭션을 실행한 검증은 아니며 운영 데이터를 변경하지 않았다.

빠른 SC→FM→SC 전환 중 첫 상세 응답을 지연하고 마지막에 반환해 오래된 수량 11이 최신 수량 77을 덮지 않는지 검사한다. 503 실패 후 Sync 재시도도 검사한다. 요청 lane 단위 테스트에서 취소/언마운트, 타임아웃, 이전 finally가 새 요청 상태를 지우지 않는지 확인한다.

지연된 사용자 설정 응답도 별도 검사했다. 기본값과 같은 저장 설정은 기본 조회 1회를 유지하고, 다른 설정은 기본값 조회 후 새 설정으로 정확히 1회 추가 조회한다. 최종 상세 요청에 적용된 가중치도 저장 설정과 일치했다.

## 검사 명령 및 제한

```text
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs run tests/lib/demand-planning tests/lib/container-planning tests/lib/planning-scenarios tests/lib/planning tests/components/planning
node node_modules/@playwright/test/cli.js test e2e/planning-load.spec.ts --reporter=line
```

- TypeScript 통과. 관련 단위/회귀 테스트 22개 파일, 259개 통과.
- 최종 Playwright 실행 5개 테스트 모두 통과(31.1초). 실제 API 동등성 1개, 격리된 편집 흐름 1개, 응답 순서/재시도 1개, 동일/다른 설정 적용 2개다.
- 신규/수정 훅, 상세 API/매핑/서비스/캐시/타입, 신규 테스트와 측정 스크립트의 ESLint 통과.
- 그리드 파일 전체 ESLint는 기존 2350행 `react-hooks/set-state-in-effect` 오류 1개와 기존 useMemo 의존성 경고 1개 때문에 실패한다. 이번 최적화의 effect에는 신규 진단이 없다. 관련 없는 기존 로직을 바꾸지 않기 위해 그대로 보존했다.
- 운영 빌드 성능, 서버 최초 컴파일, 실제 DB 편집 트랜잭션, 모든 자동 발주 모드의 브라우저 조합은 검증하지 않았다. 자동 발주의 대표 모드 UI 검사와 기존 계산 단위 테스트로 범위를 한정한다.
